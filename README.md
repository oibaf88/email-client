# Domain Mail

Self-managed domain email appliance with its own web UI, SMTP submission, SMTP
receiving, IMAP storage, antispam, DKIM, DMARC, MTA-STS, TLS-RPT, and TLS/ECDHE
transport encryption.

The Flask app is the custom UI/UX. The mail-server core is provided by
`docker-mailserver`, which bundles proven Postfix, Dovecot, Rspamd, OpenDKIM,
OpenDMARC, Fail2Ban, and related mail components. This project is intended to
run on your own VPS with your own domain, not on Render as the MX server and not
with Supabase as the mailbox store.

## What this stack includes

- Custom webmail UI for real mailbox login, folders, message reading, deletion,
  and sending.
- Dockerized SMTP receiver on port `25`.
- Authenticated SMTP submission on `587` and optional SMTPS on `465`.
- IMAPS on `993`.
- Redis-backed server-side sessions for the web UI.
- Caddy HTTPS reverse proxy for `webmail.example.com` and MTA-STS hosting.
- Let's Encrypt certificate workflow for the mail and web hostnames.
- Strict outbound SMTP TLS policy: messages are not delivered to remote MX hosts
  that do not advertise STARTTLS.
- DNS templates for MX, SPF, DKIM, DMARC, MTA-STS, TLS-RPT, and rDNS.

## What this stack does not promise

- It is not end-to-end encryption. TLS/ECDHE protects transport, so recipients
  read normally, but the receiving mail server can still see stored mail.
- It cannot be fully hosted on Render, because a real domain mail server needs
  port `25`, static IP reputation, reverse DNS, and MX delivery.
- It does not use Supabase for mailbox storage; mail lives in the Dovecot mail
  store on the VPS.

## Files

- `compose.yaml` runs the full appliance.
- `Dockerfile` packages the custom Flask web UI.
- `infra/mailserver/mailserver.env` configures docker-mailserver.
- `infra/mailserver/config/postfix-main.cf` applies strict TLS and relay policy.
- `infra/caddy/Caddyfile` serves the web UI and MTA-STS over HTTPS.
- `infra/scripts/issue-cert.sh` requests Let's Encrypt certificates.
- `infra/scripts/bootstrap-vps.sh` starts the stack, creates the first mailbox,
  and generates DKIM keys.
- `infra/scripts/mailbox.sh` manages mailbox accounts after bootstrap.
- `infra/scripts/alias.sh` manages forwarding aliases.
- `infra/scripts/renew-cert.sh` renews certificates and reloads services.
- `infra/scripts/check-mailserver.sh` checks DNS and TLS endpoints.
- `infra/dns-records.example.md` lists the DNS records to publish.

## VPS requirements

- Linux VPS with Docker and Docker Compose v2.
- Static public IPv4 address.
- Reverse DNS/PTR configurable to `mail.example.com`.
- Public inbound/outbound TCP ports: `25`, `465`, `587`, `993`, `80`, `443`.
- Recommended minimum: 2 vCPU, 4-8 GiB RAM, 40+ GiB disk for small personal use.

## Quick start on a VPS

```bash
cp .env.example .env
nano .env
```

Set your real domain values:

```env
MAIL_DOMAIN=example.com
MAIL_HOSTNAME=mail
MAIL_FQDN=mail.example.com
WEBMAIL_FQDN=webmail.example.com
MTA_STS_FQDN=mta-sts.example.com
CERT_NAME=mail.example.com
ACME_EMAIL=admin@example.com
POSTMASTER_ADDRESS=postmaster@example.com
FIRST_MAILBOX=admin@example.com
FIRST_MAILBOX_PASSWORD=use-a-long-random-password
```

Point DNS `A` records for `mail`, `webmail`, and `mta-sts` to the VPS first.
Then run:

```bash
chmod +x infra/scripts/*.sh
infra/scripts/issue-cert.sh
infra/scripts/bootstrap-vps.sh
```

After bootstrap, publish the DKIM TXT record generated by docker-mailserver, then
verify:

```bash
infra/scripts/check-mailserver.sh
```

Open:

```text
https://webmail.example.com
```

## Mailbox administration

The product has its own end-user webmail UI. Server administration happens on
the VPS so it is not exposed to the public web interface:

```bash
infra/scripts/mailbox.sh list
infra/scripts/mailbox.sh add user@example.com
infra/scripts/mailbox.sh update user@example.com
infra/scripts/mailbox.sh delete user@example.com

infra/scripts/alias.sh list
infra/scripts/alias.sh add info@example.com admin@example.com
infra/scripts/alias.sh delete info@example.com admin@example.com
```

## Local web UI development

Local development only runs the Flask UI. It still needs reachable IMAP/SMTP
services for real login and mail operations.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
flask --app app run --debug
```

On Windows PowerShell:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
Copy-Item .env.example .env
flask --app app run --debug
```

## API

- `POST /api/login`
- `POST /api/logout`
- `GET /api/folders`
- `GET /api/messages?folder=INBOX`
- `GET /api/messages/<uid>?folder=INBOX`
- `POST /api/messages/<uid>/read?folder=INBOX`
- `DELETE /api/messages/<uid>?folder=INBOX`
- `POST /api/send`

All write endpoints except login require the `X-CSRF-Token` returned by
`GET /api/state`.
